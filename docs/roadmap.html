02 · Architecture

One core, thin shells

The durable asset is not a framework or platform shell. It is a stable document model plus a deterministic rendering engine that can be hosted by the web, desktop, mobile, and automation tools.

Selected foundation: shared TypeScript domain and rendering packages

Browser APIs, native file access, and cloud services remain replaceable adapters.

Decided
@picturesque/core

Plain data, explicit commands

Contains no DOM or canvas objects. A project is serializable; every mutation travels through a typed command and can be tested without a UI.

@picturesque/render

One visual truth

Comparison previews, editor previews, thumbnails, and final exports evaluate the same scene model and color adjustments.

@picturesque/ui

Tools are interaction policy

Selection, hover, guides, and transient tool state stay outside the saved document and translate gestures into core commands.

apps/web

Browser reference shell

Hosts the canonical experience using browser-native input, IndexedDB, file handles where available, and offline assets.

apps/desktop

Native capability, minimal policy

Tauri owns operating-system integration. Product logic remains in shared TypeScript unless profiling proves a native need.

python/picturesque

Automation after stability

A Python package becomes worthwhile after the document schema can support durable batch rendering, validation, and migration.

04 · Immediate work

The first three changes

Keep each change reviewable and preserve the working comparison product throughout the migration. Structural groundwork lands before feature expansion.

Change 1 · Toolchain

Introduce Vite and strict TypeScript

Add the typed build alongside the existing runtime, keep the page and data behavior stable, then make type and production-build checks mandatory.

  • Strict compiler configuration
  • Vite development and production builds
  • Typed test setup and CI baseline
Change 2 · Core

Extract and type pure modules

Convert project, renderer, storage contracts, and ZIP logic. Add schema types, migration fixtures, and contract tests before UI state is moved.

  • Versioned project schema
  • Legacy compatibility fixtures
  • Deterministic render cases
Change 3 · Application

Separate commands from the UI

Convert the application entry point, move saved mutations behind a command interface, and establish the boundary needed for undo, redo, tools, and future platform shells.

  • Document store and command dispatcher
  • Transient view and tool state
  • Undo and redo foundation

05 · Decision record

Commit now, defer responsibly

Early decisions protect momentum; deferred decisions preserve options. Every provisional choice has an explicit point at which evidence replaces assumptions.

Decision Status Rationale or trigger
TypeScript is primary Decided Best fit for one web-first UI and portable application core.
Local-first is the default Decided Core workflows work offline; source images are not uploaded implicitly.
Legacy projects remain readable Decided Schema versions and fixtures protect existing work through migration.
Tauri for desktop packaging Provisional Confirm after the core boundary and web production build are stable.
Tauri Mobile or Expo Prototype Choose from gesture latency, memory, export, and native integration evidence.
GPU or Rust acceleration Deferred Add only after profiling identifies a stable, high-value bottleneck.
Python package Deferred Publish when the schema supports useful automation and batch rendering.
Cloud collaboration Deferred Consider after the editor is stable; keep it optional and portable.
Selected

Shared TypeScript core

Keeps domain logic close to every interactive client, minimizes bridges, and preserves a direct path from browser prototype to desktop and mobile shells.

Not selected

Python-centered application core

Strong for offline processing and automation, but introduces a deployment or runtime bridge in browsers and mobile clients. Python remains a later companion instead.

Open gate

Mobile shell choice

No framework commitment until a small editor prototype tests real assets, multitouch gestures, text input, export memory, and platform sharing.

06 · Quality bar

Trust is a product feature

Image work is valuable and often private. Reliability, fidelity, accessibility, and recoverability are release criteria—not cleanup tasks after a feature ships.

Privacy

Network activity is explicit. Core projects remain usable offline and export to a portable local file.

Visual fidelity

Preview and export share a renderer; golden fixtures cover filters, transforms, text, and blend behavior.

Recoverability

Atomic saves, migrations, undo history, crash recovery, and clear missing-asset behavior protect user work.

Accessibility

Keyboard parity, visible focus, screen-reader names, reduced motion, contrast, zoom, and touch targets ship with tools.

Performance budgets

Interaction latency, memory, startup, and export budgets are measured on representative projects before native release.

Compatibility

Versioned schemas, fixtures, and migrations keep saved projects readable across applications and releases.

Risk Early signal Response
UI orchestration stays too coupled Small features require edits across event, state, rendering, and persistence code. Extract commands and the document store during TypeScript migration.
Project format drifts Old files need ad hoc branches or platform-specific repair. Centralize schema versions, migrations, validation, and compatibility fixtures.
Rendering outgrows Canvas 2D Measured interaction or export budgets fail on representative projects. Keep a renderer interface; add workers, GPU, or Rust at profiled hotspots.
Platform behavior diverges Each shell accumulates its own project or editing rules. Use thin adapters and run shared contract fixtures in every shell.
Desktop assumptions fail on mobile Gesture conflict, memory pressure, or cramped controls appear in the prototype. Prototype before choosing the shell; redesign workflows for touch where needed.
Connected features weaken privacy Core actions silently depend on accounts, uploads, or inaccessible cloud state. Require explicit capability boundaries and portable local recovery paths.

07 · Design review

Questions that change the plan

These choices affect dependency order or architecture. Smaller feature priorities can be decided inside the relevant milestone.

Is comparison still the product’s entry point?

Keeping it first funds a reliable core before broader design tools arrive.

Should desktop precede the complete template system?

Earlier native files may be more valuable than deeper composition for production workflows.

Which mobile workflow must be excellent first?

Comparison, quick templates, camera import, or full editing will favor different shells and layouts.

Is Python automation a real early customer need?

A concrete batch workflow should exist before a public package creates a second compatibility surface.

How long should cloud collaboration remain out of scope?

Deferring it preserves focus and privacy; bringing it forward changes identity, storage, and conflict design.
